# CargoGuard · 跨境售后 RAG Agent

> 一个面向跨境网购消费者的售后维权参谋：读得懂订单、找得到法条、说得清边界，且在不确定时敢说「我不知道」。

🌐 **在线演示**：<https://cargo-guard-m6sopr3tsl3q3kua3d9hmz.streamlit.app/> ｜ 演示订单号：`ORD-1007`（输入「1007 我刚下单不久」即可触发完整链路）

跨境售后是一个**信息不对称 + 法域碎片化 + 结果不可承诺**的场景。消费者通常不知道「我这件事归哪国法律管」「商家说的包邮不包税到底谁付」「商家跑路了钱还能不能要回来」；而大多数 AI 助手在这个场景里的典型失败方式不是答不上来，而是**过度自信地编造**——编一个不存在的法定退货期、编一个听起来很像的条款号、或者顺着用户的情绪承诺「一定能退」。

这个项目围绕「如何让 Agent 在这个场景里既有用又不撒谎」来设计。下面不只写功能，也写每个设计背后的判断、踩过的坑和做过的取舍。

---

## 1. 先明确问题：三个绕不开的约束

在动手写代码前，先把难点摆清楚。跨境售后 Agent 的难度不在「调用模型」，而在三个结构性约束：

**约束一：法域不由模型决定。**
同一个「7 天无理由」，在韩国是法定的，在日本网购场景下并不存在，在美国则根本没有联邦统一规则、要看商家政策和各州法律。模型先验里对这些国家的印象大量来自国内自媒体转述，直接相信它必然出错。所以**法域判定必须由系统决定，不能交给模型自由发挥**。

**约束二：法规是有生命周期的。**
今天正确的条文，明年可能被修订。一个把法条写进 prompt 的项目，本质上是在制造一堆会过期的硬编码。所以法规必须是**可替换、可复核、可废弃**的数据，而不是提示词里的常量。

**约束三：LLM 的幻觉是概率性的，不是逻辑性的。**
你不能通过「请勿编造」这一句话消除幻觉——它只是降低了概率。真正可靠的做法是**结构性防御**：让模型没有编造的素材（无覆盖就明确告知）、让输出接受独立校验（另一个模型按规则判定）、让不可逆动作必须过人（写操作挂起审批）。

三条约束推导出三条设计原则：**法域显式化、法规数据化、防幻觉结构化**。

## 2. 设计原则

| 原则 | 含义 | 落到代码里 |
|---|---|---|
| 法域显式化 | 国家判定有明确优先级，冲突时取最可信来源 | 用户在**本轮**陈述的国家 > 规划器推断 > 订单收货国；三者冲突时不沿用旧订单 |
| 法规数据化 | 法规是数据条目，不是提示词文本 | `kb/laws/*.yaml` + `kb/facts.csv`，带版本、复核日期、废弃标记 |
| 承认不知道 | 无覆盖时明确说无覆盖，禁止用「常理」补全 | 提示词红线 + 运行时注入硬约束 + 回归用例覆盖 |
| 结果不承诺 | 只给维权路径与依据，不承诺退款结果 | 九段式输出固定含免责声明；校验器拦截「保证退款」类表述 |
| 不可逆动作必需人 | 写操作在执行前挂起，等待人工确认 | `create_escalation` → `interrupt` → `Command(resume)` |

## 3. 架构：一张图，九个节点

Agent 用 LangGraph 组织为状态图（`app/after_sales_agent.py`），节点按「理解 → 取证 → 生成 → 自检」四个阶段拆分：

```
START
  └─ intent            轻量意图分类（售后 / 订单查询 / 闲聊 / 恶意）
       └─ load_memory  注入长期记忆（国家、品类偏好、沟通偏好）
            ├─ summarize    对话过长时先压缩摘要
            └─ plan         ReAct 规划：决定调哪些只读工具
                 ├─ approval   命中写操作 → interrupt 挂起，等人审
                 └─ retrieve   复用或补检索知识库
                      └─ answer    生成九段式回答
                           └─ review    独立合规校验（软失败）
                                └─ extract_memory  结构化落记忆（不存原文）
END
```

**为什么这样切？**

- **`intent` 单独成节点**：绝大多数咨询是「查一下订单到哪了」，不需要 RAG 也不需要长回答。把分类前置，用一个几十 token 的小请求完成分流，能省掉后面整条链路的成本。这是本项目最大的成本优化点。
- **`plan` 与 `answer` 分离**：取证（调工具、查库）和写作（生成回答）是两种能力，混在一起会导致模型在写作时"顺手"编造没查到的事实。分开后，`answer` 只能基于 `plan` 阶段真实取回的数据说话。
- **`review` 是独立模型调用**：让生成者自检，等于让同一个人给自己判卷。这里用独立 prompt 按固定清单核对（无来源法规、与订单规则冲突、无法兑现承诺、遗漏跨境风险），不通过时输出问题清单而不是直接改写——避免校验器把回答改得更糟。
- **`extract_memory` 在最后且只存结构化字段**：记忆里是「所在国家：德国」「品类偏好：电子产品」这样的键值，**不存原始对话**。手机号、地址这类敏感信息不进记忆，也不进向量库。

## 4. 关键决策与取舍

### 4.1 法域判定：优先级、冲突处理与四处协同

最初的实现是「有订单号就用订单收货国」。看起来合理，实际踩了一个坑：

> 用户上一轮问了韩国订单 ORD-1002 的物流；下一轮问「我在美国买的鞋子尺码不对，运费该我出吗」——没有给订单号。系统复用了上一轮的订单，于是按韩国《电子商务消费者保护法》回答"签收起 7 天撤销权"，还引用了韩国消费者院。用户当场指出：这是美国，应该用美国法规。

根因不是知识库错，而是**状态继承比用户明示更强势**。修复不是改一句提示词，而是在四个环节上同时落实优先级。

**优先级定义**

```
买家本轮陈述的国家  >  规划器推断的国家  >  订单收货地址的国家
```

三者的可信度依据不同：陈述是用户当下的真实意图（还有可能是他自己搞错了，所以要提示差异）；规划器推断来自本轮语义，可能被上一轮带偏；订单地址是历史事实，但可能不是本轮讨论的对象。

**环节一：识别陈述国家**（`app/agent_act.py`）

```python
def stated_country_iso(query: str) -> str:
    """用户本轮明确说出的国家（ISO 码）：优先级高于订单地址与长期记忆。"""
    low = (query or "").lower()
    for hint, code in _COUNTRY_ISO.items():
        if hint in low:
            return code
    return ""
```

匹配用「中英文国名子串 → ISO 码」的映射表，刻意保持廉价：不调模型、不做 NER。另配 `mentions_us_state()` 识别加州、纽约等州名，因为美国场景需要下沉到州法。这类识别宁可漏（漏了就退回订单国家）也不能误判（误判会直接换错法域）。

**环节二：检索节点按优先级取值**（`app/agent_act.py` 的 `retrieve`）

```python
country, state_code = buyer_region(order.get("shipping_address") or "")
stated = stated_country_iso(state.get("query") or "")
if stated:
    country, state_code = stated, ""        # 陈述优先，同时清空州码
elif plan.get("country_code"):
    country = str(plan["country_code"]).upper()
```

注意这里 `state_code = ""`：一旦切到陈述国家，就不能带着别的国家的州码继续检索（否则会出现「美国 + 加州」匹配到别的州条目）。接下来把 `country` / `state_code` 传给 `kb_search`。

**环节三：工具层不再被模型参数带偏**（`app/agent_tools.py`）

只改 `retrieve` 不够——规划器在 ReAct 循环里也可能自己调 `search_knowledge_base(country_code="KR")`。所以工具内部重新做一次同样的判定：

```python
from app.agent_act import stated_country_iso
stated = stated_country_iso(state.get("query") or "")
```

原则是：**同一份事实只允许有一个裁判**。模型传参只作为建议，用户陈述才是最终依据。

**环节四：跨轮订单继承前做国家校验**（`app/after_sales_agent.py`）

```python
def _inherited_order_id(message: str, config: dict[str, Any]) -> str:
    prev_order_id = str(prev.get("order_id") or "").strip()
    if not prev_order_id:
        return ""
    stated = act.stated_country_iso(message)
    if stated:
        prev_cc, _ = act.buyer_region(prev_order.get("shipping_address") or "")
        if prev_cc and prev_cc.upper() != stated:
            return ""          # 国家冲突 → 不继承
    return prev_order_id
```

并且在冲突时**显式写入空 `order_id`**（`payload["order_id"] = ""`）。这一行看似多余，其实是修复的关键：LangGraph 的 checkpoint 会保留上一轮状态，不主动清空，下一轮、下下轮都可能继续被污染。真实故障往往不是"这一次取错了"，而是"取错之后一直错"。

**输出侧的三条硬要求**（`app/agent_answer.py`）

法域判定正确还不够，回答必须让用户看见这个判断：

| 情形 | 强制输出 |
|---|---|
| 陈述国家与订单国家不一致 | 必须说明差异，请买家确认订单是否正确，不得沿用订单国法条 |
| 美国场景 | 必须说明「无联邦统一退货/冷静期法、各州规定有差异」 |
| 美国 + 未提州 | 必须追问所在州；已提州则按该州口径作答，但仍提示州际差异 |

这段约束不是写死在系统提示词里，而是按本轮状态**拼进系统消息**的：

```python
note = [f"【买家本轮说明的收货国家】{stated}（以本轮陈述为准，法规必须按该国适用）"]
if order_cc and order_cc.upper() != stated:
    note.append("订单记录为 ...，与买家陈述不一致，回答中必须说明该差异 ...")
```

原因是：系统提示词是"长期规则"，模型容易在长上下文里稀释它；写进本轮系统消息是"当期约束"，权重更高。

**检索侧的配套：国家/州隔离与加权**（`app/kb.py` 的 `search`）

即使法域判定对了，向量检索仍可能召回别国条文。所以在打分前先做隔离：

```python
# 法规类文档只保留 tag 命中目标国（或目标州 / 欧盟）的条目
if cc and kind == "law" and not (doc_tags & target_tags):
    continue

score = 0.55 * vec_scores[i] + 0.45 * (kw_scores[i] / max(1, max_kw))
if cc and kind == "law" and (doc_tags & target_tags):
    score += 0.12                                   # 属地法优先
    if state_code and cc == "us" and f"us-{state_code}" in doc_tags:
        score += 0.08                               # 州级精确命中再加权
```

三个设计点：
1. **隔离只作用于 `law`**。`rule-*`（跨境通用规则，如包邮≠包税）和 `platform-*` 是跨国的，按国家过滤会把有用规则滤掉。
2. **欧盟国家映射到 `eu` 标签**，避免德国用户召回到法国条文、或反而召回不到欧盟通用规则。
3. **权重是硬的**：向量 0.55 + 关键词 0.45 的混合分，再叠加 0.12 / 0.08 的属地加权。属地权重必须足够大，否则语义相近的邻国条文会挤掉正确条目。


### 4.2 知识库准入：为什么要区分「人工准入」和「代码强制准入」

法规条目只采信政府消费者保护机构官网、官方法条文本、官方消费者指南。自媒体、代购攻略、论坛帖子、跨境博主、第三方中介文章一律拒收——不是保守，而是这类内容在跨境场景下的错误率高得离谱，且错误方向高度一致（都喜欢夸大买家权利）。

但「只信一级来源」是一条**流程规范**，规范靠人守，代码管不了。所以准入被拆成三层，只有第二层是代码强制的：

| 层 | 谁负责 | 机制 | 失败后果 |
|---|---|---|---|
| 来源准入 | 人 | 只收录官方来源，人工核对链接可用 | 收错源 → 错误进入知识库 |
| 状态准入 | 代码 | 加载时校验 `review_status: passed`，否则整条跳过 | 未过审条目**根本无法被检索到** |
| 法域准入 | 代码 | 检索时按国家/州 tag 隔离（见 4.1） | 召回别国条文被过滤 |

**状态准入的实现位置很关键：在加载阶段，不在检索阶段。**

`app/kb.py` 读取 YAML 时用正则解析头部字段，未通过审核的直接 `continue`：

```python
review_status = re.search(r"^review_status:\s*(.+)$", text, flags=re.M)
review_status = review_status.group(1).strip().lower() if review_status else ""
# 双人审核门槛：仅 review_status=passed 的法规可入库检索，未标注/未过审一律跳过
if review_status != "passed":
    continue
```

这里有两个刻意的决定：

1. **放在加载侧而不是 `search()` 里**。检索入口不止一个（规划器工具、检索节点、评测脚本），在每个入口加过滤条件，迟早漏一个；放在加载侧，脏数据根本不存在于内存索引中，任何路径都绕不过去。
2. **缺省即拒绝**。字段缺失、写成 `Pending`、写成 `passed `（带空格已 strip）以外的任何值，全部视为未过审。默认值必须是「不可用」，而不是「可用」——这是安全默认原则在数据层的最小实践。

**双人审核的具体流程**

```
整理人：按官网原文提炼摘要 → 填 review_status: pending_review
复核人：对照 source_url 逐条校对 → 通过则改 passed，有争议保持 pending_review
灌库：  review_status: passed 的条目才进入索引
```

摘要的撰写约束同样是准入的一部分：仅提炼与跨境网购直接相关的子集（冷静期/无理由退货、错发破损责任、进口税费纳税义务人、例外排除品类），**原文模糊则摘要也模糊**，不扩写、不引申、不自行解读法条。这条规则的存在是因为一次真实返工：日本条目被写成「通信販売有 8 天冷却期」，泰国被写成「有 7 天无理由退货」——两个国家的规则方向都写反了，模型照着错误的库里答，语气还很确定。

**两类数据、两套约束**

`kb/` 下有两种数据源，准入规则不同：

| 数据 | 形态 | 约束 |
|---|---|---|
| `kb/laws/*.yaml`（5 个国家） | 结构化法规条目 | 必须 `review_status: passed`；检索时受国家/州 tag 隔离 |
| `kb/facts.csv`（30 条） | `kind,tag,topic,正文` 四列 | 不强制审核字段；`rule-*` / `platform-*` 属跨国规则，**不受国家隔离** |

`facts.csv` 的 `kind` 直接决定检索行为：`kind == "law"` 才参与国家过滤，`rule`（包邮≠包税、错发责任）与 `platform`（平台规则）必须对所有国家可召回，否则美国用户会检索不到「包邮不等于包税」这种跨国常识。

**法规时效：约定与现状**

按领域分两档复核周期：消费者基础权利（冷静期、退货权）12 个月，海关/关税/VAT/进口政策 6 个月。法条更新时新建版本、旧版标 `deprecated: true` 保留历史，不覆盖。

需要说明的是：**`deprecated` 目前是人工约定，代码没有自动排除**。现有强制门禁只有 `review_status: passed` 一项，因此弃用时正确做法是把条目的 `review_status` 改成非 `passed`（或移出目录），而不是只加一行 `deprecated: true`。这一点已列入第 10 节待改进项——把它写成"已实现"会让维护者误以为有保护。

**改知识库必须重建索引**

`kb/chunks_emb.json` 是本地向量缓存，key 为 chunk 内容。改了 YAML 或 CSV 之后不重建，检索会继续用旧向量、旧文本：

```python
# app/kb.py
build_index()   # 内容变更后执行，重建 kb/chunks_emb.json
```

这个坑实际踩过：修好日本/泰国法规后直接跑回归，结果仍按旧结论回答，排查半天才发现是索引没重建。所以代码改动和知识库改动的验证流程必须区分——前者跑测试即可，后者必须重建索引后重跑，且索引文件要随内容一起提交。

**检索失败时宁可空白，不可脑补**

检索节点对超时和异常做了显式降级：超时返回 `retrieved=[]` 与 `rag_error="timeout"`，异常则记录 `rag_failed` 并附带错误栈，随后由回答节点走「知识库暂无相关规则」的路径，而不是让模型自由发挥。系统提示词第一条就写明：

> 只能依据【知识库检索结果】【订单信息】【用户长期记忆】回答；检索结果没有覆盖的规则，必须明确说"知识库暂无相关规则"，不得编造天数、条款号、费用、平台政策。

模型调用本身失败时还有一层兜底：降级为**严格摘录模式**，只拼接订单与知识库原文、给出来源链接，不生成任何结论。


### 4.3 无覆盖国家：必须输出「我不知道」

这是项目里最反复的一次返工。第一版跑文档用例时，13 条文本用例通过了 9 条，4 条失败全部是同一类问题：

| 用例 | 失败表现 |
|---|---|
| 日本网购无理由退货 | 声称「日本通信贩卖法定 8 天冷静期」（日本通信販売并无冷却期） |
| 泰国无强制无理由 | 编造「泰国法定 7 天无理由退货」 |
| 韩国 7 天冷静期 | 漏掉例外品类，且写出具体条款号「第 17 条」 |
| 小众国家（冰岛） | 知识库无该国条目，仍给出「14 天 + 1997 年第 48 号法」 |

四条的共性：**知识库没有依据，模型用先验补齐了，而且语气很自信。**

三层修复：

1. **知识库纠错**：日本、泰国条目本身写错了，先改数据（这是根因，不是模型问题）；
2. **提示词红线**：明确「凡知识库无对应国家条目，禁止给出任何法定天数或条款号，只能说明未覆盖并引导核实官方来源」；
3. **国家级硬约束注入**：识别用户提到的国家后，把该国法规要点**强制拼进用户消息**，优先级高于模型先验。这一条是关键——单靠系统提示词里的规矩，模型仍会时不时"回忆"起旧印象；把约束写进用户消息，实际效果才稳定。

修复后 13/13 通过，其中日本、泰国、冰岛三条都能正确表达「无法定权利 / 知识库暂无该国规则」。

### 4.4 图片证据：视觉模型只做翻译，不做判断

商品破损、商家聊天记录、物流截图、订单截图这类输入，链路是：

```
图片 → 视觉模型转结构化要点（只描述看到什么）→ 注入 Agent 上下文 → 正常 RAG 流程
```

视觉模型被严格限制为**提取器**：原样转写文字、描述画面，不评价真伪、不给维权建议。早期版本让视觉模型自由发挥，出现了「这张截图日期是未来的」这类评论，反而让下游 Agent 变得畏手畏脚，不敢对明显的破损下判断。

同样地，物流截图需要 Agent 主动计算停滞天数（结合当前日期），超过 10 天直接判定为履约异常并建议并行发起平台售后——这条规则也是测试暴露的：不写进提示词，模型只会说「建议联系商家催促」。

### 4.5 写操作：为什么必须挂起等人

`create_escalation`（创建升级工单、转平台介入）是唯一的高风险写操作。规划阶段发现写操作时**不执行**，只产生 `pending_action`，由 `approval` 节点 `interrupt` 让整张图挂起；人工通过 API 确认后才 `Command(resume)` 恢复并落库，拒绝则只记录、不写入。

这里有个实现细节值得记：`interrupt` 是 LangGraph 的控制流信号，必须原样向上抛，**不能被节点的 try/except 当成异常吞掉**——否则图会假装正常结束，写操作失去拦截。

### 4.6 成本：把钱花在该花的地方

- 闲聊、越界请求在 `intent` 节点就被拦截，不触发检索与长回答；
- 规划阶段检索过的内容在 `retrieve` 节点直接复用（`rag_reused_from_plan`），避免重复 embed 与检索；
- 同一订单短时间内重复查询走缓存；
- RAG `top-k` 按问题复杂度动态调整，简单问题少取文档；
- 长期记忆只存结构化键值，压缩后注入，不把历史原文反复塞进上下文。

### 4.7 多轮对话：短回答要接住上一轮的问题

真实对话里，买家不会每轮都把问题说完整。上一轮助手问「您用的是 PayPal、信用卡还是平台内支付？」，这一轮买家只回「WeChat」——如果系统把「WeChat」当成一条独立的新问题去做意图分类和检索，就会完全跑偏：检索结果变成微信相关，回答也接不上维权的上下文。

判定一条消息是不是「在回答上一轮」，用两种廉价且确定的信号，刻意没有交给模型：

- **长度信号**：`len(text) <= 8`，或不含疑问词且上一轮助手消息带问号、整段不超过 40 字；
- **追问提示词**：命中 `_FOLLOWUP_HINTS`（如「是的」「对」「不是」）。

为什么不用模型判断？短消息的意图判定恰恰是模型的弱项——上下文太少，它自己也拿不准，而且每轮多一次调用既贵又慢。用「长度 + 上一轮是否提问」做启发式，是把一个**确定性的结构信号**前置，让模型只在剩下真正需要语义的地方发力。

判定之后要在两个环节同时落地，缺一不可：

1. **检索侧**（`_build_search_query`）：把上一轮的 user 问题拼到本轮 query 前面再检索，否则「WeChat」根本召不回支付维权的规则；
2. **回答侧**（`_followup_context`）：注入【多轮承接】块，把上一轮的问答显式喂给模型，否则模型看到孤立的「WeChat」仍不知道该回答什么。

这个拆分本身也是个教训：只改检索不改回答，模型还是会答非所问——**承接是全链路的，不是某一个节点的事**。

### 4.8 法域确证：购买地 ≠ 收货国 ≠ 发货国，三者必须分别确认

跨境售后里最容易混淆、也最容易被模型糊弄过去的三个概念：**购买地**（在哪买的）、**收货国**（包裹寄到哪）、**发货国**（从哪发出）。用户一句「我在澳大利亚买的」，只说明购买地——它既不能直接当收货国，也不能当发货国。但模型的语言直觉会忍不住把「澳大利亚」套进法条，于是出现按澳大利亚消费者法回答、实际包裹寄到中国的错误。

修复不是改一句提示词，而是把「什么才算确认」固化成代码口径：

| 概念 | 只有满足以下表述才算确认 | 代码 |
|---|---|---|
| 收货国 | 含「收货/收件/寄到/寄往/送到/shipping address」且含国家 | `_SHIP_TO_WORDS` + `_stated_destination` |
| 发货国 | 含「发货/发件/商家从/从哪个国家发」且含国家 | `_ORIGIN_ASK_WORDS` |
| 购买地 | 含「在 X 买的/下的单」——**不**触发任何法域确认 | 仅用于排除，不写入记忆 |

追问策略按「信息可得性」排序：

1. **有可查订单**：收货国直接取订单收货地址、发货国取发件地址，据此作答并说明依据，**禁止再问**收发货国或订单号（提示词规则 16）；
2. **无订单**：缺哪项问哪项，**一次只问一项**，且国别追问的优先级高于商品细节与签收时间；
3. 两项都没有、也没说明平台：先问「是否在本平台下单、订单号是多少」。

回答侧在订单已加载时注入【订单国别】块，明确标注「已确证；禁止再问收货国/发货国」。这是因为系统提示词是「长期规则」，模型在长上下文里会稀释它；写进本轮系统消息是「当期约束」，权重更高。

这条规则的根因是一次真实反馈：用户给了订单号 ORD-1007，系统仍追问「收货地址在哪个国家」——订单里明明写着收货在中国、发货在德国。模型有数据却不用，不是它不知道，而是**没有被强制禁止再问**。

`kb/facts.csv` 里专门补了一组「中国出口 + 澳大利亚进口」的跨境退运条目（出口报关、澳方生物安全、退运关税与 GST、禁限进口品、客服话术），正是因为这条规则要求：涉及海关/关税时必须**同时**覆盖发货国出口规定与收货国进口规定，缺一边都可能被扣货或退回。

### 4.9 来源正确性：法域未确认时，法条不注入也不展示

这是一次被用户直接截图指出的线上 bug：用户说「我在亚马逊买的」（没给国别），回答底部的参考来源却出现了「澳大利亚消费者法-au / 瑕疵担保责任（欧盟）/ 德国撤回权」——三条没有一条和问题相关。

根因在 `retrieve_node`：当 `country` 为空时，`kb.search` 不对 `kind == "law"` 做法域隔离，向量语义会把最相近的法条召回出来，而「澳大利亚消费者法」这类标题在语义上和「售后维权」高度相关，排序反而靠前。

修复是检索后的一道硬过滤：

```python
if retrieved and not country:
    # 收货国未确认：法规类没有可适用的法域，不注入也不作为来源
    retrieved = [item for item in retrieved
                 if ((item.get("meta") or {}).get("kind") or "") != "law"]
```

**为什么宁可来源为空，也不展示一条不相关的法条？** 因为来源列表是用户最直观判断「这个 Agent 靠不靠谱」的地方。展示一条错的法条，比没有来源更损害信任——而且模型一旦拿到错法条，就会照着它答，错误会从「来源展示」扩散到「回答内容」。空来源 + 一句「知识库暂无相关规则」反而是诚实的。

配套地，长期记忆提取也做了同源防污染：「我在澳大利亚买的」不写进「所在国家/地区」（只有命中 `_RESIDENCE_WORDS`，即「我住在/收货地址在/寄到」这类表述才记）。否则一条错误的购买地记忆会在后续所有轮次持续误导法域判定，变成「取错之后一直错」。

### 4.10 已确认的国别要从历史累积，避免反复追问

多轮对话的另一个体验痛点：用户已经答过「收货在中国」「发货在 AU」，下一轮系统又问「收货地址在哪个国家」。这不只是啰嗦，它传递的信号是「这个 Agent 没有记忆」，直接摧毁信任。

`confirmed_countries(state)` 从整段 `history` 里累积已确认的收货国和发货国，接受两种来源：

- **买家主动陈述**：消息含收货/发货关键词且能识别出国家；
- **问答承接**：助手问了「收货地址是在 X 国吗？」，下一条 user 回答里的国家。

累积结果用在三个地方：

1. **检索隔离**：`retrieve_node` 里本轮 `country` 为空时，取 `confirmed["destination"]` 作为检索法域；
2. **回答约束**：注入【已确认国别（买家此前已答复，禁止重复询问）】块；
3. **裸国码识别**：用户回答追问时往往只回一个两字母国码（如「AU」「CN」），`stated_country_iso` 增加了裸码匹配，否则「AU」会被当成无意义文本漏掉。

这里的设计判断是：**已确认的事实属于「会话状态」，应该跨轮持久，而不是每轮重新问。** LangGraph 的 checkpoint 天然保留了 history，所以累积逻辑只读 history 即可，不需要额外的存储。

### 4.11 订单号容错：裸数字要查库校验后才认

最后一个看似小、实际很影响演示的问题：用户输入「1007 我刚下单不久」，原正则只匹配 `ORD-\d{3,}`，裸的 `1007` 识别不了，系统回退成「查不到订单，请提供正确的订单号」——明明数据里有 ORD-1007。

修复是「候选提取 + 存在性校验」两步：

```python
def _extract_order_id_candidates(text):
    ids = [m.upper() for m in re.findall(r"ORD-\d{3,}", text, flags=re.I)]
    if ids:
        return list(dict.fromkeys(ids))          # 完整格式优先
    return list(dict.fromkeys(
        f"ORD-{num}" for num in re.findall(r"(?<!\d)\d{4,}(?!\d)", text)
    ))                                            # 否则裸数字补前缀
```

然后在 `load_memory_node` 里逐个候选查库，**命中才采用**，查不到则回退到会话已有订单。

关键在第二步的存在性校验：裸数字会误匹配年份（「2026 年有什么新规」）、金额、数量。如果不查库就认，会把一个不存在的订单号塞进状态，后续 retrieve、answer、来源全部跟着错。**查库命中是唯一可靠的判据**——这和「法域未确认不展示法条」是同一个原则：宁可不确定，也不要确定地错。

## 5. 知识库结构

### 5.1 法规条目（`kb/laws/*.yaml`，按国家分文件）

真实条目结构（以美国为例，节选）：

```yaml
law_id: law-us-01
review_status: passed          # 准入开关：非 passed 在加载阶段整条丢弃
country: 美国
country_code: US               # 检索 tag：US / EU 成员会额外映射 eu
law_name: 无联邦统一网购冷静期法（州法：加州消费者救济法、纽约州消费者保护法）
applicable_scope: 美国境内线上购物、跨境直邮卖给美国消费者
core_rule:
  cooling_period: none（联邦层面无法定冷静期）
  start_from: 以商家公示退货政策为准
  right: 退货权利主要来自商家公示政策；州法禁止商家刻意隐藏退货规则
  freight_rule: 买家自行选错尺码/单纯不喜欢且无 free returns 时买家承担；
                商家尺码表错误、货不对板属商家责任，运费商家承担；
                订单标注 free returns 则商家承担
exception:
  - 商品已使用影响二次销售（外穿磨损、鞋盒吊牌破损）
  - 部分品类按商家公示政策限制
notice_requirement: 州法要求商家不得隐藏退货条件；free returns 以结算页标注为准
refund_deadline: 以商家公示政策为准；留意 restocking fee 补货费
complaint_channel: 州消费者保护机构 / 平台介入
```

字段设计上的两个考虑：

- **`core_rule` 拆成四问**（有没有权利 / 从何时起算 / 运费谁出 / 例外是什么），因为这正是买家实际会问的四件事。写成整段文字，模型容易只抓住其中一句。
- **`country_code` 同时充当检索 tag**。加载时被拆成 `meta.tags`，供国家隔离与加权使用；欧盟成员国会额外映射到 `eu`，美国可按州追加 `us-<state>`。

### 5.2 事实与规则（`kb/facts.csv`）

30 条，四列结构（含中国出口 + 澳大利亚进口的跨境退运场景条目，见 4.8）：

```csv
kind,tag,topic,正文……
rule,free_returns,包邮≠包税,包邮仅指运费，进口税费可能仍由买家承担……
platform,shein,平台托管规则,平台托管订单买家可直接发起售后，商家无权单方面驳回……
```

`kind` 决定检索行为：只有 `law` 参与国家隔离，`rule` / `platform` 对所有国家可召回（见 4.2）。

### 5.3 向量索引（`kb/chunks_emb.json`）

本地缓存的 chunk 向量，`build_index()` 生成。**内容变更必须重建并随代码一起提交**，否则检索会继续命中旧文本——这个坑在 4.2 已说明。

检索侧的整体排序意图是「订单标注的商家规则 > 平台规则 > 通用法规」：对具体订单而言，商家自己写下的承诺比通用法条更有约束力。

除法规外还有 `rule-*`（跨境通用规则，如包邮≠包税、错发责任）与 `platform-*`（平台规则）两类条目，检索时按「订单标注的商家规则 > 平台规则 > 通用法规」排序——因为对具体订单而言，商家自己写下的承诺比通用法条更有约束力。

## 6. 评测：为什么是四层，而不是一个准确率

只报一个「通过率」的项目无法定位问题。这里把评测拆成四层，每层回答不同的问题：

| 层次 | 方式 | 回答的问题 | 规模 |
|---|---|---|---|
| 确定性门禁 | 纯规则，不调模型 | 防线有没有被破坏？（工具越权、记忆投毒、订单号伪造） | 11 条红队攻击 |
| 检索质量 | gold set，离线可跑 | 该找的条文找到了吗？排序对吗？ | 22 条，HitRate@4 / MRR / Coverage |
| 记忆质量 | 离线 | 该注入的记忆注入了吗？摘要压缩后信息还在吗？ | 8 条记忆 + 2 条摘要 |
| 端到端 | 真实 Agent + 独立 LLM Judge | 回答是否满足必须要点、是否出现禁止话术？ | 20 条回归 + 25 条校验用例 + 18 项特性测试 |

**为什么端到端要用独立 Judge 而不是关键词匹配？** 因为这类回答的合格标准是语义的（「是否解释了各州差异」），关键词匹配既会漏判也会误判。Judge 的好处是能判断语义，代价是它自己也会漂移——所以 Judge 只做**判定**，不参与生成，且判定标准写成结构化清单（must_have / must_not），减少自由发挥空间。

端到端失败时的处理也刻意设计成自动的：`auto_regress.py` 跑完全部用例后，把失败原因交给模型去**改写 system prompt**，最多迭代 3 轮，每轮重新全量回归，最终输出 Markdown + JSON 报告。这不是"让模型自我修复"的浪漫想象，而是把提示词调优变成一个可复现、有记录的过程——失败项、修改点、复测结果都留在报告里。

开发期还用一份 18 条场景用例（13 条文本 + 5 条图片）做过实测，覆盖日本/韩国/美国/德国/泰国/冰岛、关税争议、签收未收货、商家跑路、发错货、物流停滞、越界请求与图片举证。第一轮 16/18，修复两条规则后 18/18——两条失败分别是「签收未收到未点名具体索赔计划」和「物流截图未主动计算停滞天数」，都属于**模型不会主动做的推理动作，必须写进规则**的情况。

## 7. 可观测性

每轮请求生成 `agent.turn → agent.node.* → agent.tool` 的嵌套 span，以结构化 JSON 写日志，字段含 `trace_id` / `span_id` / `parent_span_id` / `ms` / `status` 与业务属性；`turn_end` 带同一 `trace_id`，可直接聚合整条链路。

每轮还会记录：工具调用与成败、检索命中的文档 ID、LLM 的 prompt/completion token、校验结果、ReAct 轮数与停止原因。排查幻觉时，这些字段能直接回答「模型当时看到了什么、依据哪条文档说的」。

`/metrics` 暴露轮次、降级率、工具成功率、token 成本与 p50/p95 延迟。可选接入 OpenTelemetry 与 LangSmith，未安装依赖时自动跳过，不影响主流程。

环境变量：

| 变量 | 必填 | 作用 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 是 | 文本生成（维权策略、合规校验、记忆提取）；主应用据此判断 `has_llm()` |
| `SILICONFLOW_API_KEY` | 否 | 视觉识图（Qwen3-VL）与向量 embedding（bge-m3）；未配置则图片无法识别、embedding 回退关键词检索 |
| `TEXT_MODEL` | 否 | 覆盖文本模型，默认 `deepseek-chat` |
| `VISION_MODEL` | 否 | 覆盖视觉模型，默认 `Qwen/Qwen3-VL-8B-Instruct` |
| `SUPPORTPILOT_REVIEW_MODE` | 否 | 校验模式 `soft`（默认，只记录不拦截）/ `hard` / `off` |
| `SUPPORTPILOT_ENABLE_LONG_MEMORY` | 否 | 长期记忆开关，默认 `true` |
| `SUPPORTPILOT_RAG_TIMEOUT` | 否 | 检索超时秒数，默认 `8.0`，超时降级为「暂无规则」 |
| `SUPPORTPILOT_CONTEXT_TOKEN_BUDGET` | 否 | 触发摘要压缩的上下文 token 预算，默认 `3200` |

> 密钥读取顺序：环境变量 → 项目根目录 `.env` → Streamlit Secrets 面板（云端部署）。`.env` 不应提交（已在 `.gitignore` 中），切勿把个人密钥写进仓库。

回归脚本 `auto_regress.py` 兼容 `OPENAI_API_KEY` / `DEEPSEEK_API_KEY` / `SILICONFLOW_API_KEY` 任一，并支持 `OPENAI_BASE_URL` / `AGENT_MODEL` / `JUDGE_MODEL`（默认 DeepSeek）。

## 10. 已知局限

诚实说明比粉饰缺点更有价值：

- **知识库只覆盖 5 个国家**（US / JP / KR / TH / DE）。覆盖之外一律走「未覆盖」路径，这保证了安全，但也意味着对冰岛、巴西这类国家的用户帮助有限。扩充需要人工校对，不能靠模型生成。
- **Judge 也是模型**，判定存在抖动。缓解方式是结构化清单 + 只判不改，但没有彻底消除；同一用例偶尔会出现跨轮次的判定差异。
- **法规时效靠人工守**：6 个月 / 12 个月的复核周期是流程约定，没有定时任务，也没有到期自动预警；`deprecated: true` 目前不会被代码自动排除，弃用条目必须改 `review_status` 才会真正失效（见 4.2）。
- **准入依赖人工校对**，`review_status` 只保证"有人签过字"，不保证签得对——日本/泰国条目写反的那次事故就是流程执行到位、内容判断出错。
- **图片链路为单轮视觉提取**，多图关联（如同一订单的聊天 + 物流 + 商品）尚未做跨图一致性校验。
- **多语言只做界面与状态联动**，法条引用保留官方语言原文，未做法条级翻译，避免法律表述在翻译中失真。
