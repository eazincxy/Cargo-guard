# CargoGuard · 跨境售后 RAG Agent

> 一个面向跨境网购消费者的售后维权参谋：读得懂订单、找得到法条、说得清边界，且在不确定时敢说「我不知道」。

跨境售后是一个**信息不对称 + 法域碎片化 + 结果不可承诺**的场景。消费者通常不知道「我这件事归哪国法律管」「商家说的包邮不包税到底谁付」「商家跑路了钱还能不能要回来」；而大多数 AI 助手在这个场景里的典型失败方式不是答不上来，而是**过度自信地编造**——编一个不存在的法定退货期、编一个听起来很像的条款号、或者顺着用户的情绪承诺「一定能退」。

这个项目围绕「如何让 Agent 在这个场景里既有用又不撒谎」来设计。下面不只写功能，也写每个设计背后的判断、踩过的坑和做过的取舍。

---

## 1. 先明确问题：三个绕不开的约束

在动手写代码前，先把难点摆清楚。跨境售后 Agent 的难度不在「调用模型」，而在三个结构性约束：

**约束一：法域不由模型决定。**
同一个「7 天无理由」，在韩国是法定的，在日本网购场景下并不存在，在美国则根本没有联邦统一规则、要看商家政策和各州法律。模型先验里对这些国家的印象大量来自国内自媒体转述，直接相信它必然出错。所以**法域判定必须由系统决定，不能交给模型自由发挥**。

**约束二：法规是有生命周期的。**
今天正确的条文，明年可能被修订。一个把法条写进 prompt 的项目，本质上是在制造一堆会过期的硬编码。所以法规必须是**可替换、可复核、可废弃**的数据，而不是提示词里的常量。

**约束三：LLM 的幻觉是概率性的，不是逻辑性的。**
你不能通过「请勿编造」这一句话消除幻觉——它只是降低了概率。真正可靠的做法是**结构性防御**：让模型没有编造的素材（无覆盖就明确告知）、让输出接受独立校验（另一个模型按规则判定）、让不可逆动作必须过人（写操作挂起审批）。

三条约束推导出三条设计原则：**法域显式化、法规数据化、防幻觉结构化**。

## 2. 设计原则

| 原则 | 含义 | 落到代码里 |
|---|---|---|
| 法域显式化 | 国家判定有明确优先级，冲突时取最可信来源 | 用户在**本轮**陈述的国家 > 规划器推断 > 订单收货国；三者冲突时不沿用旧订单 |
| 法规数据化 | 法规是数据条目，不是提示词文本 | `kb/laws/*.yaml` + `kb/facts.csv`，带版本、复核日期、废弃标记 |
| 承认不知道 | 无覆盖时明确说无覆盖，禁止用「常理」补全 | 提示词红线 + 运行时注入硬约束 + 回归用例覆盖 |
| 结果不承诺 | 只给维权路径与依据，不承诺退款结果 | 九段式输出固定含免责声明；校验器拦截「保证退款」类表述 |
| 不可逆动作必需人 | 写操作在执行前挂起，等待人工确认 | `create_escalation` → `interrupt` → `Command(resume)` |

## 3. 架构：一张图，九个节点

Agent 用 LangGraph 组织为状态图（`app/after_sales_agent.py`），节点按「理解 → 取证 → 生成 → 自检」四个阶段拆分：

```
START
  └─ intent            轻量意图分类（售后 / 订单查询 / 闲聊 / 恶意）
       └─ load_memory  注入长期记忆（国家、品类偏好、沟通偏好）
            ├─ summarize    对话过长时先压缩摘要
            └─ plan         ReAct 规划：决定调哪些只读工具
                 ├─ approval   命中写操作 → interrupt 挂起，等人审
                 └─ retrieve   复用或补检索知识库
                      └─ answer    生成九段式回答
                           └─ review    独立合规校验（软失败）
                                └─ extract_memory  结构化落记忆（不存原文）
END
```

**为什么这样切？**

- **`intent` 单独成节点**：绝大多数咨询是「查一下订单到哪了」，不需要 RAG 也不需要长回答。把分类前置，用一个几十 token 的小请求完成分流，能省掉后面整条链路的成本。这是本项目最大的成本优化点。
- **`plan` 与 `answer` 分离**：取证（调工具、查库）和写作（生成回答）是两种能力，混在一起会导致模型在写作时"顺手"编造没查到的事实。分开后，`answer` 只能基于 `plan` 阶段真实取回的数据说话。
- **`review` 是独立模型调用**：让生成者自检，等于让同一个人给自己判卷。这里用独立 prompt 按固定清单核对（无来源法规、与订单规则冲突、无法兑现承诺、遗漏跨境风险），不通过时输出问题清单而不是直接改写——避免校验器把回答改得更糟。
- **`extract_memory` 在最后且只存结构化字段**：记忆里是「所在国家：德国」「品类偏好：电子产品」这样的键值，**不存原始对话**。手机号、地址这类敏感信息不进记忆，也不进向量库。

## 4. 关键决策与取舍

### 4.1 法域判定：为什么优先级必须是「本轮陈述 > 订单 > 推断」

最初的实现是「有订单号就用订单收货国」。看起来合理，实际踩了一个坑：

> 用户上一轮问了韩国订单 ORD-1002 的物流；下一轮问「我在美国买的鞋子尺码不对，运费该我出吗」——没有给订单号。系统复用了上一轮的订单，于是按韩国《电子商务消费者保护法》回答"签收起 7 天撤销权"，还引用了韩国消费者院。用户当场指出：这是美国，应该用美国法规。

根因不是知识库错，而是**状态继承比用户明示更强势**。修复方式有两层：

1. `stated_country_iso()` 从本轮文本里识别国家（中英文，含美国州名），命中即作为最高优先级；
2. 跨轮继承订单前先做国家校验——**用户陈述的国家与订单收货国冲突时，直接不继承订单**，并显式清空 `order_id`，避免残留状态继续污染后续轮次。

同时补了一条输出规则：国家冲突时必须说明「我按您说的 X 国判断，这与订单记录的 Y 国不一致」，并对美国场景**必须讲清无联邦统一法、各州有差异，并追问所在州**。

这类问题的通用教训：**多轮 Agent 里，最危险的不是模型幻觉，而是未被清除的上下文状态。**

### 4.2 知识库：为什么只信一级来源，且必须双人审核

法规条目只采信政府消费者保护机构官网、官方法条文本、官方消费者指南。自媒体、代购攻略、论坛帖子、跨境博主、第三方中介文章一律拒收——不是保守，而是这类内容在跨境场景下的错误率高得离谱，且错误方向高度一致（都喜欢夸大买家权利）。

流程上是**整理人写摘要 → 复核人对照官网校对 → 标记 `review_status: passed` 才允许入向量库**。检索侧默认过滤条件固定为：

```json
{"review_status": "passed", "deprecated": false}
```

有争议或条文含糊的条目标记 `pending_review`，宁可检索不到，也不给出半可信的答案。

时效管理上按领域分两档复核周期：消费者基础权利（冷静期、退货权）12 个月，海关/关税/VAT/进口政策 6 个月。法条更新时**新建版本**，旧版标 `deprecated: true` 保留历史，不覆盖。临近复核到期的文档会在输出时追加预警。

### 4.3 无覆盖国家：必须输出「我不知道」

这是项目里最反复的一次返工。第一版跑文档用例时，13 条文本用例通过了 9 条，4 条失败全部是同一类问题：

| 用例 | 失败表现 |
|---|---|
| 日本网购无理由退货 | 声称「日本通信贩卖法定 8 天冷静期」（日本通信販売并无冷却期） |
| 泰国无强制无理由 | 编造「泰国法定 7 天无理由退货」 |
| 韩国 7 天冷静期 | 漏掉例外品类，且写出具体条款号「第 17 条」 |
| 小众国家（冰岛） | 知识库无该国条目，仍给出「14 天 + 1997 年第 48 号法」 |

四条的共性：**知识库没有依据，模型用先验补齐了，而且语气很自信。**

三层修复：

1. **知识库纠错**：日本、泰国条目本身写错了，先改数据（这是根因，不是模型问题）；
2. **提示词红线**：明确「凡知识库无对应国家条目，禁止给出任何法定天数或条款号，只能说明未覆盖并引导核实官方来源」；
3. **国家级硬约束注入**：识别用户提到的国家后，把该国法规要点**强制拼进用户消息**，优先级高于模型先验。这一条是关键——单靠系统提示词里的规矩，模型仍会时不时"回忆"起旧印象；把约束写进用户消息，实际效果才稳定。

修复后 13/13 通过，其中日本、泰国、冰岛三条都能正确表达「无法定权利 / 知识库暂无该国规则」。

### 4.4 图片证据：视觉模型只做翻译，不做判断

商品破损、商家聊天记录、物流截图、订单截图这类输入，链路是：

```
图片 → 视觉模型转结构化要点（只描述看到什么）→ 注入 Agent 上下文 → 正常 RAG 流程
```

视觉模型被严格限制为**提取器**：原样转写文字、描述画面，不评价真伪、不给维权建议。早期版本让视觉模型自由发挥，出现了「这张截图日期是未来的」这类评论，反而让下游 Agent 变得畏手畏脚，不敢对明显的破损下判断。

同样地，物流截图需要 Agent 主动计算停滞天数（结合当前日期），超过 10 天直接判定为履约异常并建议并行发起平台售后——这条规则也是测试暴露的：不写进提示词，模型只会说「建议联系商家催促」。

### 4.5 写操作：为什么必须挂起等人

`create_escalation`（创建升级工单、转平台介入）是唯一的高风险写操作。规划阶段发现写操作时**不执行**，只产生 `pending_action`，由 `approval` 节点 `interrupt` 让整张图挂起；人工通过 API 确认后才 `Command(resume)` 恢复并落库，拒绝则只记录、不写入。

这里有个实现细节值得记：`interrupt` 是 LangGraph 的控制流信号，必须原样向上抛，**不能被节点的 try/except 当成异常吞掉**——否则图会假装正常结束，写操作失去拦截。

### 4.6 成本：把钱花在该花的地方

- 闲聊、越界请求在 `intent` 节点就被拦截，不触发检索与长回答；
- 规划阶段检索过的内容在 `retrieve` 节点直接复用（`rag_reused_from_plan`），避免重复 embed 与检索；
- 同一订单短时间内重复查询走缓存；
- RAG `top-k` 按问题复杂度动态调整，简单问题少取文档；
- 长期记忆只存结构化键值，压缩后注入，不把历史原文反复塞进上下文。

## 5. 知识库结构

按国家分文件存储，每个条目是标准字段：

```yaml
law_id: law-jp-001
country_code: JP
cooling_period: 无（通信販売无法定冷却期）
start_from: 签收日
freight_rule: 无强制规定，以商家公示为准
exception: 商品有瑕疵/错发时适用民法瑕疵担保
notice_requirement: 商家须公示退货条件
refund_deadline: 以商家条款为准
complaint_channel: 国民生活センター
```

配合 `law_manifest.csv` 维护清单（国家码、标题、链接、版本、上次复核、下次复核、状态），用于快速筛出待复核条目。

除法规外还有 `rule-*`（跨境通用规则，如包邮≠包税、错发责任）与 `platform-*`（平台规则）两类条目，检索时按「订单标注的商家规则 > 平台规则 > 通用法规」排序——因为对具体订单而言，商家自己写下的承诺比通用法条更有约束力。

## 6. 评测：为什么是四层，而不是一个准确率

只报一个「通过率」的项目无法定位问题。这里把评测拆成四层，每层回答不同的问题：

| 层次 | 方式 | 回答的问题 | 规模 |
|---|---|---|---|
| 确定性门禁 | 纯规则，不调模型 | 防线有没有被破坏？（工具越权、记忆投毒、订单号伪造） | 11 条红队攻击 |
| 检索质量 | gold set，离线可跑 | 该找的条文找到了吗？排序对吗？ | 22 条，HitRate@4 / MRR / Coverage |
| 记忆质量 | 离线 | 该注入的记忆注入了吗？摘要压缩后信息还在吗？ | 8 条记忆 + 2 条摘要 |
| 端到端 | 真实 Agent + 独立 LLM Judge | 回答是否满足必须要点、是否出现禁止话术？ | 20 条回归 + 25 条校验用例 + 18 项特性测试 |

**为什么端到端要用独立 Judge 而不是关键词匹配？** 因为这类回答的合格标准是语义的（「是否解释了各州差异」），关键词匹配既会漏判也会误判。Judge 的好处是能判断语义，代价是它自己也会漂移——所以 Judge 只做**判定**，不参与生成，且判定标准写成结构化清单（must_have / must_not），减少自由发挥空间。

端到端失败时的处理也刻意设计成自动的：`auto_regress.py` 跑完全部用例后，把失败原因交给模型去**改写 system prompt**，最多迭代 3 轮，每轮重新全量回归，最终输出 Markdown + JSON 报告。这不是"让模型自我修复"的浪漫想象，而是把提示词调优变成一个可复现、有记录的过程——失败项、修改点、复测结果都留在报告里。

开发期还用一份 18 条场景用例（13 条文本 + 5 条图片）做过实测，覆盖日本/韩国/美国/德国/泰国/冰岛、关税争议、签收未收货、商家跑路、发错货、物流停滞、越界请求与图片举证。第一轮 16/18，修复两条规则后 18/18——两条失败分别是「签收未收到未点名具体索赔计划」和「物流截图未主动计算停滞天数」，都属于**模型不会主动做的推理动作，必须写进规则**的情况。

## 7. 可观测性

每轮请求生成 `agent.turn → agent.node.* → agent.tool` 的嵌套 span，以结构化 JSON 写日志，字段含 `trace_id` / `span_id` / `parent_span_id` / `ms` / `status` 与业务属性；`turn_end` 带同一 `trace_id`，可直接聚合整条链路。

每轮还会记录：工具调用与成败、检索命中的文档 ID、LLM 的 prompt/completion token、校验结果、ReAct 轮数与停止原因。排查幻觉时，这些字段能直接回答「模型当时看到了什么、依据哪条文档说的」。

`/metrics` 暴露轮次、降级率、工具成功率、token 成本与 p50/p95 延迟。可选接入 OpenTelemetry 与 LangSmith，未安装依赖时自动跳过，不影响主流程。

## 8. 运行

```bash
pip install -r requirements.txt
# .env 中配置 OPENAI_API_KEY（或其他 openai 兼容接口 key）
streamlit run streamlit_app.py
```

Docker：

```bash
docker build -t cargoguard .
docker run --rm -p 8501:8501 --env-file .env cargoguard

# API 模式
docker run --rm -p 8000:8000 --env-file .env cargoguard \
  uvicorn app.api:app --host 0.0.0.0 --port 8000
```

人工审批示例：

```bash
# 1) 触发写操作：返回 needs_approval=true，不落库
curl -X POST http://localhost:8000/chat -H "Content-Type: application/json" \
  -d '{"order_id":"ORD-1004","message":"商家失联，帮我升级投诉","thread_id":"demo-1"}'

# 2) 人工确认后恢复执行
curl -X POST http://localhost:8000/approval -H "Content-Type: application/json" \
  -d '{"thread_id":"demo-1","approved":true,"reviewer":"alice","note":"核实属实"}'
```

评测与回归：

```bash
python tests/redteam_eval.py                         # 红队防线（无需模型）
python tests/retrieval_eval.py --min-hit-rate 0.9    # 检索门禁
python tests/memory_eval.py                          # 记忆与摘要质量
python auto_regress.py                               # 端到端回归（需要 API Key）
python auto_regress.py --dry-run                     # 仅校验用例结构
```

环境变量：`OPENAI_API_KEY`（回归必填）、`OPENAI_BASE_URL` / `AGENT_MODEL` / `JUDGE_MODEL`（可选，默认 DeepSeek）。

## 10. 已知局限

诚实说明比粉饰缺点更有价值：

- **知识库只覆盖 5 个国家**（US / JP / KR / TH / DE）。覆盖之外一律走「未覆盖」路径，这保证了安全，但也意味着对冰岛、巴西这类国家的用户帮助有限。扩充需要人工校对，不能靠模型生成。
- **Judge 也是模型**，判定存在抖动。缓解方式是结构化清单 + 只判不改，但没有彻底消除；同一用例偶尔会出现跨轮次的判定差异。
- **法规复核依赖人工流程**，6 个月 / 12 个月的周期是策略而非自动执行；到期预警只在输出侧提示，尚未接入定时任务自动提醒。
- **图片链路为单轮视觉提取**，多图关联（如同一订单的聊天 + 物流 + 商品）尚未做跨图一致性校验。
- **多语言只做界面与状态联动**，法条引用保留官方语言原文，未做法条级翻译，避免法律表述在翻译中失真。
